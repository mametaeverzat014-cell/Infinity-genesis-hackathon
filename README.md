# auditgym — RL-среда для дообучения моделей финансового аудита

Кейс 1, FinTech. Воспроизводимый симулятор ИИ-аудитора. Среда генерирует синтетическую
компанию за один отчётный период, вносит скрытые финансовые ошибки с записанной причинной
историей, даёт агенту узкий набор инструментов только для чтения и оценивает выводы по
эталону с доказательствами. Это среда для RL, а не платёжное приложение и не чат-бот: веса
модели она не обновляет.

* Контракт `reset`/`step` в стиле Gymnasium, JSON-совместимый, лимит 100 шагов, страницы по 50 строк.
* 4 независимо настраиваемых типа ошибок (10 вариантов), 2 сценария взаимодействующих ошибок,
  чистые компании и 10 видов правдоподобных корректных отвлекающих случаев.
* Общий опубликованный matcher и терминальная награда из раздела 05 кейса, тесты на атакующие ответы.
* Оценщик работает в другом процессе, чем агент. Эталон, seed и диагностика не попадают в наблюдения.
* Независимая проверка данных: бухгалтерские равенства до внесения ошибки, доказуемость каждого
  расхождения по его набору доказательств, полнота эталона (эталонный аудитор без доступа к эталону
  находит ровно заявленные ошибки).
* Только стандартная библиотека Python 3.11. Без сети, без GPU, без платных API.

## Быстрый старт: единая команда проверки

```bash
python3 -m auditgym check            # ~45 с на 2 ядрах, код возврата 0 = всё прошло
```

Или в контейнере, без сети:

```bash
docker build -t auditgym:1.0.0 .
docker run --rm --network none --cpus 2 --memory 4g auditgym:1.0.0
```

`check` выполняет пять шагов и пишет `runs/check/check_report.json`, `report.md`,
`trajectories.jsonl`, `grader_log.jsonl`:

1. юнит-тесты (`tests/`, 59 тестов на `unittest`, без зависимостей);
2. 20 открытых эпизодов (`episodes/train`, `episodes/dev`): проверка данных и эталона и
   побайтовое совпадение файлов при повторной генерации из `(seed, config, версия)`;
3. 40 свежих эпизодов (смешанные, чистые, взаимодействующие, «стресс» с 12 ошибками): проверка
   данных и эталона;
4. четыре базовые политики и scripted-эксперт на 20 эпизодах (10 смешанных, 5 чистых,
   5 взаимодействующих) в закрытом режиме, агенты в отдельных процессах; проверка отсутствия
   утечек в траекториях;
5. 20 парных проверок: смена ID и перестановка записей сохраняют ответ и награду oracle, а
   повтор seed и действий даёт ту же траекторию.

Другие команды:

```bash
python3 -m auditgym demo --policy expert --seed 1009 --config interaction   # пошаговое демо
python3 -m auditgym run --split dev --policies random,reconciler,flag_all,oracle --mode eval --out runs/dev
python3 -m auditgym verify                      # проверить episodes/train и episodes/dev
python3 -m auditgym verify --seeds 0-99 --config stress
python3 -m auditgym generate --seed 42 --config eval_mixed --out /tmp/ep42
python3 -m auditgym build-splits                # пересоздать 10 train + 10 dev эпизодов
python3 -m unittest discover -s tests -t . -v   # только тесты
```

## Эпизод и данные

Эпизод — одна компания и один месяц. Типичный размер: 300–1 200 строк журнала, 70–190
документов, 0–12 ошибок. Базовая валюта (USD, EUR, KZT, GBP, JPY), 1–3 иностранные валюты
(в том числе JPY с разрядностью 0 и KWD с разрядностью 3), фиксированное смещение часового
пояса от −08:00 до +09:00, год и месяц периода меняются от seed.

Публичные файлы (`episodes/<split>/<ep>/public/`, агенту доступны только через инструменты):

| Файл | Поля |
|---|---|
| `manifest.json` | `schema_version`, `env_version`, `config_version`, `config_sha256`, `episode_id`, `base_currency`, `currency_exponents`, `period_start`, `period_end` (не включается), `timezone`, `counts`, `rounding` |
| `ledger.csv` | `row_id, timestamp, account, debit_minor, credit_minor, currency, entity_id, invoice_id, payment_id, journal_id` |
| `invoices.jsonl` | `doc_id, invoice_id, entity_id, customer_name, issued_at, due_at, currency, total_minor, po_ref, line_items[]` |
| `payments.jsonl` | `doc_id, payment_id, entity_id, kind (receipt/refund), timestamp, currency, amount_minor, invoice_refs[]/null, refund_of, bank_reference` |
| `fx.csv` | `fx_id, date, source_currency, target_currency, rate` |
| `policy.json` | учётная политика: выбор даты курса, границы периода, округление, определения типов, сумм, `affected_ids` и доказательств |

Форматы: время — ISO-8601 со смещением (документы приходят из разных систем: в UTC или в
местном времени); деньги — целые минимальные единицы; курсы — десятичные строки с 6 значащими
цифрами; отсутствующие ссылки — явный `null` (в CSV — литерал `null`). Курсы есть только по
рабочим дням, политика требует взять последний доступный курс не позже даты. Журнал ведётся
в базовой валюте, поэтому сравнить документ в другой валюте с журналом можно только после
конвертации.

Закрытые файлы (`private/`, только у оценщика): `truth.json` (`issue_id`, `type`, `variant`,
`scenario`, `affected_ids`, `expected_amount_minor`, `currency`, `evidence_sets`) и
`provenance.json` (seed, полная конфигурация, план, пропуски, отвлекающие случаи и для каждой
ошибки — `setup` и `changes`: вставки, удаления и изменения строк «до/после», вставки документов).

## Ошибки

| Тип | Варианты | Что видно в записях | Сумма (базовая валюта) |
|---|---|---|---|
| `duplicate_invoice` | `duplicate_document`, `double_posting` | второй счёт с тем же `po_ref` и теми же строками или вторая проводка AR того же счёта | дебет AR дублирующей проводки |
| `payment_allocation` | `missing`, `partial` | `invoice_refs` платежа применяют X к счёту, а AR кредитован меньше; остаток ушёл в 2300 или на другой счёт | ожидаемый кредит AR минус проведённый |
| `fx_conversion` | `utc_date`, `wrong_date`, `inverted`, `digit_typo` | основная строка не равна конвертации по курсу на местную дату документа | \|проведено − верно\| |
| `period_cutoff` | `tz_boundary`, `backdated` | документ вне периода в часовом поясе компании, но проведён в этом периоде | проведённая основная строка |

Взаимодействующие сценарии (каждый даёт две ошибки):

* `partial_fx_payment_at_boundary` — платёж в иностранной валюте сразу после местной полуночи
  на границе периода (UTC-дата попадает в соседний период). Курс взят по UTC-дате (ошибка
  `fx_conversion`), счёт закрыт частично (ошибка `payment_allocation`). Наивная проверка периода
  по UTC здесь ещё и ложно обвинит платёж в `period_cutoff`.
* `duplicate_with_misapplied_payment` — счёт продублирован, а платёж клиента, который по
  `invoice_refs` закрывает оригинал, проведён на дубликат (`duplicate_invoice` и `payment_allocation`).

Корректные отвлекающие случаи: повторяющиеся счета с той же суммой и строками, но другим PO;
частичные поставки по одному PO; разбитые платежи; один платёж на несколько счетов; короткие
оплаты; переплаты и авансы (`invoice_refs: null`) в 2300; возвраты; документы около местной
полуночи и на границе периода, где UTC-дата и местная дата расходятся; документы следующего
периода, которые правильно не проведены; курсы выходных дней.

Каждый тип включается, выключается и настраивается отдельно (`errors.<type>.count`, `variants`),
сценарии — через `scenarios`, чистые компании — через `clean_probability` (пресеты `clean`,
`eval_clean`). Максимум 12 ошибок на эпизод.

## Контракт среды

```python
from auditgym import AuditEnv
env = AuditEnv(mode="train")                       # "eval": награда 0 для политики, оценка только в журнал
obs, info = env.reset(seed=7, config="train")      # или options={"episode_dir": "episodes/dev/03_..."}
obs, reward, terminated, truncated, info = env.step({"action": "list_records", "table": "ledger", "cursor": None, "limit": 50})
```

| Действие | Аргументы |
|---|---|
| `list_records` | `table` ∈ ledger/invoices/payments/fx, `cursor` (непрозрачный, стабильный), `limit` ≤ 50 |
| `get_record` | `table`, `id` (row_id, invoice_id/payment_id или doc_id, fx_id) |
| `get_document` | `doc_id` → полный документ (строки, `po_ref`, `bank_reference`) |
| `calculator` | `expression`: десятичные числа, `+ - * /`, скобки |
| `submit` | `findings`: объект findings.json |

* Первое наблюдение содержит задачу, manifest, политику, описание инструментов, формат ответа и
  `steps_remaining`. Шаговое наблюдение: `{kind, step, action, result, error, steps_remaining}` —
  только запрошенные записи, результат или ошибка и остаток шагов.
* Неизвестное действие, таблица, ID или курсор, неверный аргумент или ошибка калькулятора дают
  ограниченную ошибку (`code` + сообщение ≤ 200 символов, ввод не повторяется) и расходуют шаг.
* Максимум 100 шагов, включая `submit`. `submit` → `terminated=true`. Исчерпание шагов или 60 с →
  `truncated=true`, оценивается пустой ответ. Шаг после завершения возвращает `episode_finished`
  и не меняет оценку.
* Награда за исследование 0. В `train` политика получает терминальную награду и агрегированные
  метрики, в `eval` — 0; награда и диагностика пишутся только в журнал оценщика.
* `reset` строит всё состояние заново, поэтому эпизоды изолированы.

## Выводы, сопоставление и награда

Код: `auditgym/matcher.py` (функция `grade` чистая, без ввода-вывода).

* **Нормализация.** ID и коды валют приводятся через `strip().upper()`. `affected_ids` и
  `evidence_ids` — множества. `invoice_id`/`payment_id` в доказательствах заменяются на их
  `doc_id`. Тип сравнивается без учёта регистра.
* **Валидация.** Схема `schemas/findings.schema.json`: не больше 30 выводов, 10 ID доказательств,
  1 000 символов объяснения, сумма — неотрицательное целое (bool и float не принимаются),
  неизвестные ключи запрещены, `episode_id` должен совпадать. Любое нарушение даёт награду −1 и
  ошибку в журнале оценщика.
* **TP.** Совпадают тип, множество `affected_ids` с каноническим, валюта; сумма в допуске
  `|claimed − expected| ≤ max(2, floor(0.001 × expected))` минимальных единиц; доказательства
  содержат хотя бы один полный допустимый набор.
* **Сопоставление.** Один-к-одному, максимальное паросочетание (алгоритм Куна). Неоднозначности
  разрешаются детерминированно: выводы в порядке отправки, ошибки по `issue_id`. Число TP не
  зависит от порядка. Повторы и несопоставленные выводы — FP, пропущенные ошибки — FN.
* **Метрики.** `P = TP/(TP+FP)`, `R = TP/(TP+FN)`, `F1 = 2TP/(2TP+FP+FN)`. При нулевом
  знаменателе P и R равны 0. Пустой эталон и пустой ответ дают F1 = 1, пустой эталон и непустой
  ответ — F1 = 0.
* **Награда.** `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, где `inspection_steps` — все
  шаги, кроме `submit`. Возврат эпизода равен этой награде. Текст `explanation` на награду не
  влияет.
* **Строгий режим доказательств** (`env.strict_evidence`, по умолчанию выключен): в нём засчитываются
  только ID, которые агент действительно видел в наблюдениях.

Тесты (`tests/test_reward.py`) показывают: полный верный ответ лучше молчания на ошибочных
книгах; молчание лучше ложных обвинений на чистых; дубли не приносят выгоды; «пометить всё»
даёт ≤ −0.5; экономия шагов лишь немного различает равные ответы (0.1 за 50 шагов). Отдельно
проверены угаданные ID, неполные и выдуманные доказательства, чужая валюта, неверный тип,
границы допуска, нормализация, 21 вариант неверной структуры, повторная отправка и тайм-аут.

## Изоляция и защита эталона

* **Обучение.** `python -m auditgym.server` держит среду и эталон в своём процессе, `RemoteEnv`
  даёт тот же `reset`/`step`. Можно использовать и `AuditEnv` в своём процессе (открытый режим).
* **Закрытый прогон.** Оценщик (`runner.py`) держит среду у себя и запускает политику отдельным
  процессом (`agent_proc.py`). Политика получает только наблюдения и отвечает действиями. Seed,
  конфигурацию, эталон и журнал оценщика она не видит. В режиме `eval` сервер игнорирует seed и
  конфигурацию от клиента и выдаёт эпизоды из расписания оценщика.
* **Без утечек через наблюдения.** Нет путей, трассировок, «did you mean», метрик в `eval`; ID —
  случайные токены без порядка; внедрённые документы и строки неотличимы по полям и
  распределениям (секунды, смещения). `check` сканирует все траектории на поля и токены эталона.
* **Секрет seed.** Генератор открыт, поэтому по маленькому seed эпизод можно было бы
  воспроизвести. Оценщик может задать `AUDITGYM_SEED_SECRET`: ключ подмешивается во все потоки
  случайности, процесс агента его не наследует (это проверено тестом). Для закрытых seed
  рекомендуется ещё и высокая энтропия (≥ 64 бит).
* **Oracle** запускается только внутри оценщика и проверяет максимум награды, а не способность агента.

## Воспроизводимость и обобщение

* `(seed, config, ENV_VERSION)` полностью определяют эпизод. Генерация использует только
  целочисленную случайность и `Decimal`, без float и без зависимости от `PYTHONHASHSEED`
  (тест запускает генерацию в процессах с разными hash seed).
* Отдельные потоки случайности для истории, ошибок, ID (`id_salt`) и порядка (`order_salt`,
  `shuffle_records`). Поэтому смена ID и перестановка не меняют скрытую историю: oracle
  получает ту же награду, эксперт — тот же F1 (20 парных проверок в `check`).
* Конфигурации версионированы (`config_version`), а `config_sha256` и версии записаны в
  manifest и provenance.
* Открытые train/dev-эпизоды используют публичные seed 1001–1010 и 2001–2010, проверочный
  набор — 910000+. Закрытая оценка должна брать другие seed (и секрет). Пресеты для неё:
  `eval_mixed`, `eval_clean`, `eval_interaction`.

## Результаты базовых политик

20 эпизодов проверочного набора, режим `eval`, агенты в отдельных процессах (полная таблица и
разбор сбоев — в `docs/RESULTS.md`):

| политика | F1 | возврат | возврат (чистые) | возврат (взаимод.) | шаги | TP/FP/FN |
|---|---|---|---|---|---|---|
| random (seed 0) | 0.100 | −0.803 | −0.210 | −1.000 | 18.1 | 0/26/93 |
| reconciler (наивная сверка) | 0.176 | −0.676 | −1.000 | −0.524 | 22.7 | 50/369/43 |
| flag_all (атака) | 0.003 | −0.996 | −1.000 | −1.000 | 19.1 | 1/599/92 |
| oracle (только оценщик) | 1.000 | 1.000 | 1.000 | 1.000 | 1.0 | 93/0/0 |
| expert (scripted, без эталона) | 1.000 | 0.945 | 0.944 | 0.948 | 28.4 | 93/0/0 |

Scripted-эксперт решает все эпизоды без доступа к эталону, поэтому ошибки доказуемы по записям.
Наивная сверка теряет баллы именно на задуманных ловушках: часовые пояса, исторический курс,
одинаковые суммы.

## Честные ограничения

* Мир синтетический и узкий: только дебиторская задолженность (счета клиентам, поступления,
  возвраты), журнал в базовой валюте, без налогов, кредит-нот, кредиторки, переоценки остатков на
  конец периода и сторно. Высокая награда не доказывает пригодность для реального аудита.
* Учётная политика упрощена и задана явно (курс по местной дате документа, списание AR по
  историческому курсу). Агент должен следовать ей, а не реальным стандартам.
* Генератор открыт. Защита закрытой оценки держится на секретных высокоэнтропийных seed и
  (опционально) `AUDITGYM_SEED_SECRET`. Без них знающий код агент мог бы перебором найти seed.
* Сценарий `partial_fx_payment_at_boundary` требует ненулевого смещения часового пояса и
  иностранной валюты. Если ставить его некуда, он пропускается и это записывается в
  `provenance.skipped`. Измерено: 6 пропусков на 200 эпизодов пресетов `train`, `interaction`,
  `eval_mixed` и `eval_interaction`. Тест требует, чтобы в пресете `interaction` оба сценария
  присутствовали.
* «Отсутствие» записи (например, нет кредита AR по паре платёж–счёт) нельзя доказать списком ID.
  Проверка достаточности использует для таких фактов всю таблицу, это явно оговорено в `verify.py`.
* Тайм-аут 60 с измеряется по настенным часам, поэтому на очень медленной машине он может
  сработать недетерминированно. Все остальные переходы и награды детерминированы.
* Эталонный аудитор и генератор написаны одной командой по одной политике. Совпадение их
  результатов проверяет согласованность данных, но не независимую интерпретацию политики. Её
  должна дать закрытая проверка жюри.
* Обучение весов и локальная модель не входят в сдачу, демо выполнено scripted-политикой.
