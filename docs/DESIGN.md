# Записка о дизайне

## 1. Идея

Ошибка в среде — не «подозрительная строка», а **причинное изменение** согласованной скрытой
истории. Поэтому генератор работает в четыре стадии, у каждой свой поток случайности из seed:

1. **История** (`build_company`, `build_fx`, `build_entities`, `build_invoices`, `build_payments`):
   компания, период, часовой пояс, валюты, курсы (только рабочие дни, случайное блуждание в
   `Decimal`), клиенты и поставщики, счета (в том числе прошлого и следующего периода), платежи со
   всеми корректными паттернами: разбитые, на несколько счетов, короткие, переплаты, авансы,
   возвраты, платежи после конца периода.
2. **Проведение** (`post_all`): чистый журнал строится из истории по опубликованной политике.
   * Счёт: Дт 1100 / Кт 4000 по курсу на местную дату выставления.
   * Поступление: Дт 1000 по курсу на дату платежа; Кт 1100 по каждой ссылке по историческому
     курсу счёта; остаток в 2300 по курсу платежа; разница в 7900.
   * Возврат: Дт 2300 / Кт 1000.

   Шум — расходы поставщикам: Дт 6xxx / Кт 1000.
3. **Внесение ошибок** (`plan_and_inject`): транзакционно. Перед каждой попыткой берётся снимок
   состояния, неудачная попытка откатывается целиком, поэтому незаявленных расхождений не бывает.
   Каждое изменение — вставка, удаление или изменение строки «до/после» и вставка документа —
   пишется в provenance. Для каждой ошибки сразу вычисляются сумма и допустимые наборы
   доказательств.
4. **Рендер**: публичные ID — случайные токены из отдельного потока (`id_salt`), порядок —
   из отдельного потока (`order_salt`, `shuffle_records`). Поэтому «безвредные преобразования»
   не меняют историю, ошибки и суммы.

Журнал ведётся в базовой валюте. Документы в иностранной валюте можно сравнить с ним только через
`fx.csv` и политику. Отсюда ловушки на дату курса (местная или UTC, выходные), на исторический
курс при списании AR и на разрядность (JPY 0, KWD 3).

## 2. Почему эталон «настоящий»

`auditgym/verify.py` проверяет каждый эпизод независимо от генератора:

* **До внесения.** Все изменения из provenance откатываются, затем проверяются равенства: каждая
  проводка сбалансирована, строки только в базовой валюте и только с одной стороны; сумма строк
  счёта равна итогу; каждый счёт периода проведён ровно один раз по верному курсу и с меткой
  времени документа, документы вне периода не проведены; кредиты AR по платежу равны ссылкам
  `invoice_refs` по историческим курсам, остаток в 2300 по курсу платежа, ссылки согласованы по
  валюте и контрагенту; возвраты корректны.
* **После внесения.** Каждый заявленный вывод заново выводится **из записей его набора
  доказательств** и политики: два документа действительно дубликаты, а строка — проводка
  дубликата; курс в наборе — именно курс по политике; разница проведённой и верной суммы равна
  `expected_amount_minor`; документ действительно вне периода в часовом поясе компании; и так
  далее. Нельзя требовать недоступный факт: наборы доказательств содержат только публичные ID и
  не больше 10 штук.
* **Полнота.** Эталонный аудитор (`solver.py`) видит только публичные записи и `policy.json` и
  должен найти ровно эталон: ни одного лишнего расхождения, ни одной недоказуемой ошибки. Это
  проверено на сотнях seed всех пресетов. `check` каждый раз проверяет 60 эпизодов.

Противоречивые данные отсекаются конструктивно: дубликаты отличаются от повторов по `po_ref` и
строкам, частичные поставки — по строкам; каждый документ — цель не больше одной ошибки (кроме
сценариев, где взаимодействие задумано); ошибка вносится, только если расхождение материально
(≥ max(20, 1 основная единица) и ≥ 5 допусков).

## 3. Против простых трюков

| Трюк | Что мешает |
|---|---|
| Сравнить только суммы | повторяющиеся счета и частичные поставки с теми же суммами и тем же PO |
| Проверить период по UTC-дате | документы у местной полуночи: правильные по местному времени и ошибочные только по местному |
| Конвертировать по дате платежа | AR списывается по историческому курсу, разница уходит в 7900 |
| Искать 2300 как признак ошибки | авансы, переплаты и возвраты легально используют 2300 |
| Искать «странные» строки по форме | одинаковые поля и распределения (секунды, смещения, ID) у внедрённых и обычных записей |
| Пометить всё | лимит 30 выводов, точное совпадение множества ID, суммы и доказательств; FP снижает F1 |
| Повторить верный вывод | сопоставление один-к-одному: повтор — FP |
| Угадать ID | ID — случайные 8-символьные токены, совпадение `affected_ids` как множества |
| Убедительный текст | `explanation` не участвует в оценке |
| Подсмотреть эталон | другой процесс, `eval` скрывает награду, сканирование траекторий, секрет seed |

## 4. Награда

Терминальная, из раздела 05 кейса: `clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`; за
исследование 0. Масштаб стоимости шага: полный разбор занимает около 30 шагов и стоит около
0.06. На эпизоде с 12 ошибками один пропущенный TP стоит около 0.087, то есть около 43 шагов.
Поэтому экономия шагов лишь немного различает равные ответы. Молчание на чистых книгах даёт +1,
любое обвинение — −1, на ошибочных молчание даёт −1.

Свойства матчинга доказаны тестами: TP = размер максимального паросочетания, он не зависит от
порядка выводов и правила выбора при неоднозначности.

## 5. Измеренный разбор сбоев

Из журнала оценщика по 20 эпизодам проверочного набора (`docs/RESULTS.md`):

* **reconciler** (наивная сверка): 369 FP, из них около 90 % — `no_such_issue`. Это ложные
  `payment_allocation` и `fx_conversion` из-за курса по UTC-дате и курса платежа вместо
  исторического. FN сосредоточены в `fx_conversion/utc_date`, `period_cutoff/tz_boundary` и
  `payment_allocation`: именно те ловушки, ради которых они задуманы. На чистых компаниях
  возврат −1.
* **flag_all**: 599 FP на 1 случайный TP. Атака бесполезна.
* **random**: на чистых эпизодах иногда отправляет пустой ответ и получает положительную награду,
  на ошибочных всегда −1.
* **expert**: 0 FP / 0 FN, около 28 шагов. Оставшийся разрыв с oracle — только стоимость шагов.
